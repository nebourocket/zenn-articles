# 「本物のユーザー」の代わりは務まるのか？ユーザーシミュレータの評価を評価した論文を読んで

LLMエージェントがコードを書いたり、資料を作ったり、作ったものを直したりしてくれるようになってきました。こうしたエージェントを評価するとき、ひとつ困ったことがあります。エージェントの相手をする「ユーザー」が必要なんですよね。本物のユーザーを毎回集めるのはコストがかかりますし、同じ条件で比べ直すのも難しい。そこで使われるのが「ユーザーシミュレータ」です。LLMにユーザー役を演じてもらって、エージェントとの多ターンなやり取りを大量に回す。便利な仕組みだと思います。

でも、ふと気になることがあります。そのシミュレータは、本当に「本物のユーザー」の代わりになっているんでしょうか。シミュレータが作るユーザーが、やけに協力的だったり、壊れた成果物をあっさり受け入れてしまったりしたら、エージェントの評価そのものがゆがんでしまいますよね。今回は、そんな「シミュレータを評価する評価方法」そのものを検証した、ちょっと入れ子構造の論文を読んでみました。

## 今回読んだ論文

- **タイトル**: On Evaluating User Simulators for Interactive Agents
- **著者**: Hengguang Zhou, I-Hung Hsu, Li Chen, Priyanshi Shrivastava, Anastasios Angelopoulos, Wei-Lin Chiang, Ion Stoica, Cho-Jui Hsieh（UCLA、Arena）
- **arXiv ID**: [arXiv:2611.24892](https://arxiv.org/abs/2611.24892) [cs.LG]
- **公開日**: 2026年11月18日

この記事では、論文のアブストラクトと本文を読みながら、自分の言葉で整理していきます。引用は短めにして、感想を中心に書いていこうと思います。

## ユーザーシミュレータって何？なぜ必要なの？

まず前提を整理します。いまのLLMエージェントは、ユーザーと何度もやり取りしながら成果物を作ります。コードを書いてもらって、動かしてみて、「ここを直して」と伝えて、また直してもらう。そんな多ターンのやり取りです。

エージェントの性能を測るには、このやり取りを再現しないといけません。でも本物のユーザーを毎回呼ぶのは大変です。時間もお金もかかりますし、同じユーザーに同じ条件で何度も付き合ってもらうのは現実的ではありません。そこで、LLMに「このユーザーのつもりで振る舞って」とお願いして、シミュレータとして使うわけです。オフラインでのエージェント評価にも、エージェントの学習にも使われているそうです。

ここで論文が指摘するのが、シミュレータと本物のユーザーでは、エージェントの成功率の測り方が変わってしまう可能性がある、という点です。シミュレータがやけに寛容だったら、ダメなエージェントでも「成功」になってしまいます。逆に、やけに厳しかったら、良いエージェントが低く評価されてしまうかもしれません。

じゃあ、シミュレータがちゃんとしているかどうかはどうやって確かめるのか。これまでの研究では、たとえば「人間の言葉遣いや振る舞いと似ているか」「ユーザーの指定と矛盾していないか」「人間の評価と一致するか」といった観点でチェックされてきました。でも論文は、こう問いかけます。**それらのチェックは、本当に「ダメなシミュレータ」を見抜けているんでしょうか。**

## 「評価の評価」という発想：わざと壊してみる

この論文のいちばん面白いところは、評価方法そのものをテストする「メタ評価」というアイデアだと思います。やり方はシンプルで、少し意地悪です。

まず、本物のユーザーとエージェントのセッションをもとに、シミュレータの「リプレイ」を作ります。元のセッションから、作るべき成果物や制約、好み、ペルソナ、終了条件などを抜き出してプロファイルを作り、そのプロファイルをもとにシミュレータが新しいエージェントとやり取りする。これが「コントロール」です。

そして次に、このシミュレータのセットアップに、わざと「故障」を仕込みます。たとえば、ユーザーのゴールを勝手にすり替える。制約を全部取り除く。途中で会話を打ち切らせる。壊れた成果物なのに「OK」と言わせる。特定のエージェントだけをひいきさせる。そんなふうに10種類の「摂動（perturbation）」を用意して、評価方法がその故障をちゃんと見抜いてスコアを下げられるかを試すんです。

10種類の摂動は、大きく3つのレベルに分かれています。

**下流の評価としての有用性（L1）に関わるもの**

- **エージェント贔屓**: 特定のエージェントをひいきするよう指示する。ミスを大目に見て、不完全な成果物を受け入れ、温かいフィードバックを返す。
- **プロファイル抽出アーティファクト**: 元のエージェントへの不満を、ユーザーの性格そのものにしてしまう。リプレイ先のエージェントがちゃんと要件を満たしても、ずっと批判的なままになる。

**集団レベルの忠実度（L2）に関わるもの**

- **壊れた成果物の承認**: エラーや要件漏れがある成果物なのに、承認するよう指示する。
- **早期終了**: リプレイを途中で切り上げて、成果物を確認したり修正を求めたりする機会を減らす。
- **前倒し**: やり取りの中で少しずつ出てくるはずの要件や受け入れ条件を、最初のメッセージに全部入れてしまう。

**トレースレベルの忠実度（L3）に関わるもの**

- **敵対的ゴール**: 本来のゴールと成果物を、もっともらしい別のものにすり替える。
- **全制約除去**: プロファイルからハードな要件を全部取り除く。
- **ペルソナ交換**: ユーザーの文体を、対照的なものに置き換える。
- **共同デバッガー**: 問題を診断して修正方法を提案させる。ユーザーの役割を超えた手助けをさせてしまう。
- **言語切替**: 最初のメッセージのあとで、シミュレータの使う言語を変えてしまう。

どれも「言われてみれば確かにダメなユーザーだよね」というものばかりです。評価方法がこれらを見抜けないなら、その評価方法はあまり頼りにならない、というわけです。

ちなみに、この摂動の設計には、44万2,516件の本物のセッションと2万100件のリプレイの分析が使われているそうです。机上の空論ではなく、実際に起きていた失敗から作られているのが、説得力のあるところだなと思いました。

## 既存の評価方法は、どこまで見抜けたのか

結果は、なかなか厳しいものでした。

既存の評価スイートは、SimulatorArena、VISTA、SWE-Togetherという3つの先行研究から持ってきたものです。これらが10種類の摂動のうち検出できたのは、それぞれ**6個、5個、6個**。半分ちょっとしか見抜けていないんです。

さらに気になるのは、3つの評価方法がどれも「エージェント贔屓」を見抜けなかったことです。特定のエージェントをひいきするシミュレータは、エージェント同士のスコアや順位をゆがめてしまうのに、それが検出できない。評価の土台が揺らいでしまいますよね。

そしてもっと驚いたのは、壊れた成果物を承認するような摂動に対して、既存の評価方法の総合スコアが、むしろ摂動入りのリプレイのほうを高く評価してしまった、という点です。ダメな振る舞いを「良い」と判定してしまう評価方法では、エージェントの改善もへんな方向に進んでしまいそうです。

## 新しい評価スイート：3つのレベルで見る

こうした問題を受けて、論文は新しい評価スイートを提案しています。ポイントは、シミュレータを3つのレベルで見ることです。

**L1：下流のランキング一致**
シミュレーションで得られたエージェントの順位が、独立した参照順位とどれだけ一致するかをチェックします。シミュレータが「エージェントを評価する道具」として役に立つかどうか、という観点です。

**L2：集団レベルの忠実度**
シミュレーションされたユーザー集団の振る舞いのパターンが、本物のユーザー集団とどれだけ似ているかを比べます。要件をどう伝えるか、進捗やエラーにどう反応するか、いつ「完成」と判断するか、といった集団としての傾向です。

**L3：トレースレベルの忠実度**
1つひとつのリプレイが、その元のユーザーのゴールや制約、ペルソナを保っているかをチェックします。集団として似ていても、個別のセッションで別人のようになっていたらダメ、というわけです。

この3つのレベルを組み合わせた新しい評価スイートは、**10種類の摂動をすべて検出できた**そうです。既存の方法が半分ほどしか見抜けなかったのと比べると、大きな違いだと思います。

フィルタリングの性能も比べられています。スコアをしきい値として使って「ダメなシミュレーションをふるい落とす」とき、どれだけ良いものを残せるか、という観点です。

- エージェント贔屓の実験では、摂動を5%だけ通してしまうしきい値で、新しい指標はコントロール集団の**98%**を残せたのに対し、既存の最良のベンチマーク（Sim2Real）は**10%**しか残せなかったそうです。
- 壊れた成果物の承認の実験では、新しい指標（行動分布）はコントロール集団の**100%**を残せたのに対し、既存の最良のものは**26%**でした。
- トレースレベルでは、ペルソナのスコアが本物のユーザーのトレースの**68%**を残せたのに対し、既存の最良のものは**28%**だったそうです。

「悪いものを落としつつ、良いものを残す」という、フィルタとしての性能でも差が出ているのが印象的でした。

## 6つのシミュレータを実際に比べてみると

論文では、6つのシミュレータをこの新しい評価スイートで比べています。使われたのは351件の本物のマルチターンセッションで、348人の異なるユーザー、23の言語にまたがり、フルスタックのWebアプリやゲーム、デザイン素材、自動化ワークフローなどを作るやり取りが含まれているそうです。

結果として、**どのシミュレータも3つのレベルすべてでトップになることはなかった**そうです。SimulatorArenaのシミュレータは下流のランキング一致が最も高く、論文が提案するプロファイルベースのシミュレータは集団レベルとトレースレベルの忠実度でリードした、とのことです。

この「どれかひとつでは足りない」という結果は、3つのレベルを分けて見る意味を裏付けているように思います。全体として似ているかどうかだけを見ても、個別のセッションでゴールを取り違えていたり、制約を無視していたり、キャラが変わっていたりすることは見逃してしまう。論文も、集団レベルの指標だけでは、シミュレータが間違ったゴールを追ったり、制約を無視したり、キャラを崩したりすることを見逃してしまう、と指摘しています。

## 私の研究と重ねて考えてみる

私は、人間と犬のインタラクションを解析する研究をしています。犬と人の関わりの動画をアノテーションして、行動をクラスタリングしたり、状態の遷移を分析したりする、というものです。シミュレータの話とは直接は関係ないのですが、「それっぽく見えるけど、本質が違う」ことを見分ける難しさは、どこか共通しているなと感じました。

たとえば犬の行動を見ていても、表面的には同じように見える動きが、文脈によってまったく違う意味を持っていることがあります。集団として平均を取れば似ているように見えても、個々のやり取りの中では別のことをしている。そんなときに「全体の傾向」と「1回1回のやり取り」の両方を見ないと、本当のことは分からない。論文の3つのレベルという考え方は、インタラクションの分析全般に通じるものがある気がします。

あと、評価方法を「わざと壊して試す」という発想も、研究の進め方として面白いなと思いました。自分の作った指標が本当に機能しているのかを確かめるには、意図的にダメなケースを入れてみて、ちゃんと反応するかを確かめるのが手っ取り早い。犬の行動のアノテーションでも、似たようなことを考える場面があるかもしれません。まだまだ学ぶことが多いです。

## まとめ：持ち帰れるポイント

最後に、この論文から持ち帰れるポイントを3つにまとめてみます。

1. **ユーザーシミュレータの評価方法自体が、まだ万全ではない。** 既存の評価スイートは、10種類の「わざと壊した」シミュレータのうち半分ほどしか見抜けず、エージェント贔屓はどれも検出できませんでした。シミュレータのスコアが高いからといって、それが良いシミュレータだとは限らない、ということです。

2. **見るべきレベルは3つある。** エージェントの順位付けに役立つか（L1）、集団として本物のユーザーと似ているか（L2）、1つひとつのやり取りで元のユーザーの意図を保っているか（L3）。この3つを組み合わせた評価スイートは、10種類の摂動をすべて検出できたそうです。

3. **今のシミュレータに「万能」はない。** 6つのシミュレータを比べた結果、どのレベルでもトップというものはありませんでした。用途に応じて、どこを重視するか考える必要がありそうです。

エージェントがどんどん賢くなる中で、その評価を支えるシミュレータの質も問われるようになってきています。評価の評価、というちょっとややこしい話ではありますが、エージェントを使う側にとっても、作る側にとっても、避けて通れないテーマになっていくのかなと思います。
